# עדכון סטטוס מרוכז (Bulk)

עדכון סטטוס של כמה פניות בבקשה אחת (עד 100), מתוך רשימת הפניות.

## זרימה בממשק

1. אחרי סינון, המשתמש מסמן פניות בתיבות הסימון בכרטיסים, או את תיבת "בחר הכל בעמוד".
2. הבחירה חלה **רק על העמוד הנוכחי**: כל טעינה חדשה של תוצאות (מעבר עמוד, סינון, מיון, רענון) מאפסת אותה. לכן אי אפשר לשלוח יותר מגודל עמוד אחד (20), הרבה מתחת למגבלת 100 בשרת.
3. מופיע סרגל פעולות דביק: בחירת סטטוס יעד ולחיצה על "עדכן נבחרות".
4. אחרי התשובה מוצג פאנל תוצאות: מספר הצלחות, מספר כשלונות וטבלת כשלונות (פניה, סיבה, הסבר). הרשימה נטענת מחדש.

## ה-Endpoint

`POST /api/requests/bulk-status`

```json
{ "status": "InProgress", "changedByUserId": 1,
  "items": [ { "id": 10, "rowVersion": "AAAAAAAAB9E=" } ] }
```

תשובה (200):

```json
{ "requestedCount": 3, "succeededCount": 2, "failedCount": 1,
  "succeeded": [ { "...": "RequestListItemDto עם RowVersion חדש" } ],
  "failed": [ { "id": 12, "reason": "Conflict", "message": "..." } ] }
```

### ולידציה ברמת הבקשה (כל הבקשה נדחית, שום דבר לא משתנה)

| קוד | מצב |
|-----|------|
| 400 | רשימה ריקה, יותר מ-100 פניות, מזהה כפול, סטטוס לא חוקי, `rowVersion` חסר |
| 422 | המשתמש המבצע (`changedByUserId`) אינו קיים או אינו פעיל |

### כשלונות ברמת פניה (הבקשה מחזירה 200)

| `reason` | משמעות |
|----------|--------|
| `NotFound` | לא נמצאה פניה מתאימה |
| `Conflict` | `RowVersion` לא תואם: הפניה עודכנה על ידי משתמש אחר. נבדק גם בקריאה וגם ב-`WHERE` של ה-UPDATE |
| `InvalidTransition` | מעבר סטטוס אסור (New→InProgress, InProgress→Waiting/Completed, Waiting→InProgress/Completed, Completed סופי) |
| `AlreadyInStatus` | הפניה כבר בסטטוס המבוקש. מדווחת במפורש, כדי שהספירה לא תטעה |

## למה Partial Success ולא All-or-Nothing

- **הכשלונות צפויים ואינם תקלה.** בקבוצה של עד 100 פניות, סביר שאחת עודכנה בינתיים או שהמעבר שלה אסור (הסטטוס הנוכחי שונה מפניה לפניה). כשל אחד לא אמור לבטל 99 עדכונים תקינים.
- **דרישת המוצר:** המשתמש מקבל כמה הצליחו ורשימת כשלונות עם הסיבה, ויכול לטפל רק בהן.
- **פחות נעילות:** All-or-Nothing דורש טרנזקציה אחת על עד 100 שורות ונעילות ארוכות. בעומס של כמה משתמשים, כל קונפליקט היה מבטל את כולה ומגדיל את הסיכוי לנסיונות חוזרים.
- **עקביות עם עדכון בודד:** כל פניה עוברת בדיוק את אותם כללים ואותה טרנזקציה כמו `PUT /api/requests/{id}`: קיום, `RowVersion`, מעבר חוקי, עדכון `UpdatedAt` ושורת היסטוריה אטומית.
- **החיסרון:** התוצאה אינה אטומית כקבוצה, ולכן התשובה המפורטת חובה. פעולה חוזרת בטוחה: פניות שהצליחו לא ישתנו שוב. אם נשלחות עם ה-`RowVersion` החדש יחזרו כ-`AlreadyInStatus`, ואם עם הישן (שכבר אינו תקף) יחזרו כ-`Conflict`, כי בדיקת הגרסה קודמת לבדיקת הסטטוס.

## מימוש וקונקרנטיות

- הלולאה ב-`RequestsService.BulkUpdateStatusAsync` רצה פניה אחר פניה (DbContext אחד), וכל פניה נשמרת ב-`SaveChanges` נפרד: שורת הפניה ושורת ההיסטוריה באותה טרנזקציה.
- Optimistic concurrency: `RowVersion` שהלקוח קרא נשלח לכל פניה ומשמש כ-`OriginalValue`, כך ש-0 שורות מושפעות = קונקרנט אחר ניצח = `Conflict`.
- אחרי קונפליקט `ChangeTracker.Clear()` מסיר את הישות הכושלת ואת שורת ההיסטוריה שלה, כדי שלא יישמרו בטעות בפניה הבאה.
- בקשה לא תקינה נחסמת לפני כל גישה ל-DB, ובדיקת המשתמש המבצע נעשית פעם אחת.
- ביטול (`CancellationToken`): הלולאה נעצרת, ופניות שכבר נשמרו נשארות שמורות.

## Cache

ה-Summary של ה-Dashboard (ספירה לפי סטטוס ועדיפות) מתבטל פעם אחת בסוף הקריאה אם לפחות פניה אחת עודכנה, ולא אחרי כל פניה. ראו [summary-aggregations.md](summary-aggregations.md). בכמה מופעי שרת נדרש מטמון מבוזר (Redis), כמו בעדכון בודד.

## מגבלות ושיפורים

- 100 שאילתות ו-`SaveChanges` בקריאה אחת (כ-3 קריאות DB לפניה). מספיק לעמוד של 20, ואפשר לשפר עם טעינה אחת של כל הפניות (`WHERE Id IN (...)`) ועדכון בעזרת `ExecuteUpdate` עם בדיקת `RowVersion`.
- אין הרשאות: `changedByUserId` נשלח מהלקוח (`CURRENT_USER_ID = 1`).
- פניות שנבחרו בעמוד אחד אינן נשמרות במעבר עמוד, בכוונה.
