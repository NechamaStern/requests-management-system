# ביצועים על 100,000 פניות

נמדד על מסד `RequestsManagement` עם 100,000 שורות ב-`Requests`, SQL Server 2025 Express (LocalDB) ו-.NET 10, על מחשב פיתוח.
המדידות חוזרות על עצמן עם [database/performance-queries.sql](../database/performance-queries.sql), והשאילתות הן ה-SQL ש-EF Core מייצר בפועל (נלכד מלוג `Microsoft.EntityFrameworkCore.Database.Command`).

## איך נבחנה היעילות

1. **זמן API מקצה לקצה:** `curl` מול ה-API המקומי, 3 הרצות לכל בקשה (ההרצה הראשונה כוללת חימום). הזמנים כוללים כ-25-30 מ"ש הקמת תהליך `curl`.
2. **מדד מקביל ל-Query Plan:** `SET STATISTICS IO, TIME ON` (קריאות לוגיות, CPU וזמן) ותוכנית הביצוע בפועל (`SHOWPLAN_TEXT`) לכל שאילתה.
3. **ניסויי שיפור:** אותה שאילתה עם שינוי אחד (Hint או שאילתה חלופית), והשוואת הקריאות הלוגיות.

לשם ההשוואה: סריקה מלאה של הטבלה היא **1,565 קריאות** (עמודים).

## הפעולות שנבחרו

1. `GET /api/requests`: חיפוש, סינון, מיון ועימוד. הפעולה הכבדה והמרכזית.
2. `GET /api/requests/summary`: Aggregations (`GROUP BY` על כל הטבלה) עם Cache.

## פעולה 1: `GET /api/requests`

### זמני API (ms, 3 הרצות, כולל ~25-30 של curl)

| תרחיש | תוצאות | זמן |
|---|---|---|
| ללא פילטר (ברירת מחדל: `CreatedAt DESC`) | 100,000 | 245 / 59 / 48 |
| סטטוס + עדיפות + טווח תאריכים | 4,952 | 67 / 51 / 63 |
| ארגון (prefix `Acme`) | 10,061 | 133 / 39 / 44 |
| ארגון (`Acme Branch 11`) | 774 | 46 / 51 / 43 |
| מיון לפי כותרת | 100,000 | 50 / 41 / 47 |
| מטפל (`assignedTo=a`) | 76,972 | 82 / 47 / 48 |
| עמוד עמוק (עמוד 4000) | 100,000 | 143 / 139 / 150 |
| חיפוש חופשי `Payment` (נפוץ) | 9,965 | 274 / 243 / 248 |
| חיפוש חופשי `Payment` + סטטוס | 3,938 | 125 / 123 / 112 |
| חיפוש חופשי `issue #7777` (נדיר) | 16 | **682 / 712 / 565** |

ההרצה הראשונה של התרחיש הראשון (245) כוללת חימום, ולכן אינה מייצגת.

### Query Plan ומדדי IO (עמוד של 20 שורות)

| שאילתה | תוכנית | קריאות לוגיות | זמן |
|---|---|---|---|
| ברירת מחדל | `Index Scan (ORDERED) IX_Requests_CreatedAt` + Top 20 + Key Lookup | 183 | 4 ms |
| סטטוס + עדיפות + תאריכים | לא נבדקה תוכנית; 162 קריאות מעידות על שימוש באינדקס ולא בסריקה | 162 | 3 ms |
| ארגון `LIKE 'Acme Branch 11%'` | **`Clustered Index Scan`** + Sort (Top 20) | 1,565 | 19 ms |
| חיפוש `%issue #7777%` (נדיר) | `Index Scan IX_CreatedAt` + **Key Lookup לכל שורה** | **311,735** | **451 ms** |
| עמוד 4000 (`OFFSET 79980`) | לא נבדקה תוכנית; הקריאות שוות לסריקת הטבלה | 1,565 | 77-105 ms |
| `COUNT(*)` לחיפוש | `Clustered Index Scan` | 1,565 | 192 ms |

עיקרון חשוב: **לא נטען כלום לזיכרון.** כל תרחיש מחזיר מהמסד 20 שורות, ואת הספירה כשאילתת `COUNT` נפרדת (ראו [requests-list-page.md](requests-list-page.md#איך-נמנעת-טעינת-כלל-הנתונים-לזיכרון)).

### אינדקסים שנוספו ולמה

פירוט מלא ב-[database-schema.md](database-schema.md#אינדקסים). בקצרה:

- `IX_Requests_CreatedAt`: מיון ברירת המחדל ללא Sort (ראו Index Scan מסודר למעלה).
- `IX_Requests_Status_CreatedAt` (+`INCLUDE Priority`) ו-`IX_Requests_Priority_CreatedAt`: סינון לפי סטטוס/עדיפות כ-Seek, והמיון מגיע מהאינדקס. משמשים גם את ה-Aggregations.
- `IX_Requests_AssignedToUserId_CreatedAt`: סינון לפי מטפל ותמיכה ב-FK.
- `IX_Requests_OrganizationName_CreatedAt`, `IX_Requests_Title`, `IX_Requests_UpdatedAt`: סינון/מיון לפי השדות האלה.
- `IX_RequestStatusHistory_RequestId_ChangedAt`: שליפת היסטוריה לפי פנייה.

### ממצאים וצווארי בקבוק

1. **חיפוש חופשי נדיר: 311,735 קריאות (פי 200 מסריקה מלאה).** ה-Optimizer מניח שיימצאו 20 תוצאות מהר (Row Goal), לכן הוא סורק את `IX_CreatedAt` בסדר ומבצע Key Lookup לכל שורה כדי לבדוק `LIKE`. כשהמילה נדירה הוא עובר על כל 100K שורות. `LIKE '%x%'` אינו יכול להשתמש באינדקס רגיל. נוסף על כך, `COUNT` סורק את הטבלה בנפרד.
   - **ניסוי שיפור:** `OPTION (USE HINT('DISABLE_OPTIMIZER_ROWGOAL'))` מוריד ל-**1,565 קריאות** (פי 200), וזמן השאילתה מ-451 ל-197 ms. זה עדיין סריקה מלאה, אבל לא עולה פי 200 על המקרה הגרוע.
   - **פתרון נכון לפרודקשן:** Full-Text Search (או אינדקס n-gram חיצוני כמו Elasticsearch) במקום `LIKE '%x%'`.
2. **סינון ארגון: אין Seek.** הציפייה (שהייתה מתועדת) הייתה Seek על `IX_Requests_OrganizationName_CreatedAt`. בפועל ה-Optimizer בוחר Scan + Sort, ובדקנו שהוא צודק: כפיית האינדקס עולה **2,388** קריאות לעומת **1,565**, כי הפילטר תואם 774 שורות והאינדקס אינו מכסה את שאר העמודות (Key Lookup לכל שורה). Seek משתלם רק בארגונים סלקטיביים מאוד. שיפור אפשרי: `INCLUDE` של העמודות הנדרשות ב-SELECT (אינדקס מכסה), במחיר אינדקס גדול יותר.
3. **עימוד עמוק (OFFSET):** העלות גדלה עם מספר העמוד (1,565 קריאות בעמוד 4000 לעומת 183 בעמוד 1). **שיפור שנמדד:** Keyset pagination (`WHERE (CreatedAt, Id) < (@last)`) עם **288 קריאות ו-30 ms** (לעומת 1,565 ו-105 ms). לא מומש, כי הממשק מציג מספרי עמודים וקפיצה חופשית, וצריך את `OFFSET`. מומלץ אם יוסיפו גלילה אינסופית.
4. **`COUNT(*)` לכל בקשה** מוסיף סריקה בחיפוש טקסט (192 ms מתוך ~450). שיפור: לא לחשב ספירה מדויקת מעבר לסף, או להציג "יותר מ-X".

## פעולה 2: `GET /api/requests/summary`

| מדד | ערך |
|---|---|
| תוכנית | סטטוס: `Index Scan` מסודר על `IX_Requests_Status_CreatedAt` + `Stream Aggregate` (נבדק, בלי Sort ובלי קריאה ל-Clustered). עדיפות: אותו מבנה על `IX_Requests_Priority_CreatedAt` (לא נבדק בתוכנית, ה-IO תואם) |
| קריאות לוגיות | סטטוס: 335, עדיפות: 285 (לעומת 1,565 בסריקת הטבלה) |
| זמן שאילתה | 12-17 ms |
| זמן API | 34-51 ms (כולל curl) |

האינדקסים הצרים מקטינים את הסריקה פי 5. הסריקה עדיין לינארית בגודל הטבלה, ולכן הפעולה יושבת מאחורי Cache של 5 דקות עם ביטול אחרי עדכון (ראו [cache.md](cache.md)). בקשה שנענית מה-Cache אינה פונה למסד כלל.

**שיפור אפשרי:** Indexed View או טבלת מונים שמתעדכנת בעדכון, אם הטבלה תגדל למיליונים.

## מסקנות

- הפעולות הנפוצות (ללא חיפוש טקסט, עם סינון לפי סטטוס/תאריך/עדיפות) הן 3-5 ms ו-160-180 קריאות במסד.
- ה-Bottleneck המרכזי הוא החיפוש החופשי, במיוחד מילה נדירה. הוא מתועד כמגבלה ידועה ויש לו ניסוי שיפור שנמדד.
- הניסוי עם `DISABLE_OPTIMIZER_ROWGOAL` ו-Keyset לא מומשו בקוד. הם מתועדים כהצעות שיפור מבוססות מדידה.

## חזרה על המדידה

```powershell
sqlcmd -S "(localdb)\MSSQLLocalDB" -E -C -d RequestsManagement -i database\performance-queries.sql
```

להצגת תוכנית ביצוע בפועל: להוסיף `SET STATISTICS XML ON` או להפעיל Actual Execution Plan ב-SSMS.
